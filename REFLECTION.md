### Question 1

> **PO-100026 (BuyerRef "RO-2") ended with StatusCode 90, which is not in the documentation. How did you work out what it means, and what does your system now do with the stock that will never arrive?**

`90` never appears in the interface manual's documented lifecycle (`10` Accepted → `20` Picking → `30` Shipped → `40` Delivered). Watching `PO-100026` through `DeliveryTrackingJob`'s polling loop, `90` showed up once and then never changed on subsequent polls — unlike `10`/`20`/`30`, which are always followed by a later code, `90` behaved like a terminal state, the same way `40` (Delivered) does. That pattern — terminal, but not the "success" terminal code — is what a cancellation/void status looks like, so `mapLegacyStatusCode()` in `DeliveryTrackingJob` explicitly maps `"90"`, `"99"`, and the literal strings `"CANCELLED"`/`"VOID"` to our own `SupplierOrderStatus.CANCELLED`, separately from the `default` branch (which logs a warning and falls back to `UNKNOWN` for anything genuinely unrecognized).

Once an order is marked `CANCELLED`, `DeliveryTrackingJob` explicitly skips firing `StockReplenishedEvent` and only logs a warning ("was CANCELLED by supplier. No restock performed."). The `supplier_orders` row stays in the database as a permanent, honest record that this specific reorder failed — it is never silently retried or reinterpreted as delivered. The practical effect is that the units it was meant to cover simply never arrive through that reorder; if `Inventory`'s stock for that product is still below threshold, the *next* customer order that crosses the low-stock threshold will publish a fresh `LowStockEvent`, which the Notification module turns into a brand-new reorder (its own `BuyerRef`/`X-Request-Id`), independent of the cancelled one. We do not currently auto-retry a cancelled PO on a timer — that's a known limitation, not an oversight: retrying a supplier-cancelled order automatically without knowing *why* it was cancelled risked masking a real problem (e.g. a discontinued SKU) rather than a transient one.

### Question 2

> **At 19:20:39 LegacySupply was down and rejected BuyerRef "RO-2". It was eventually placed as PO-100026 at 19:22:44. Where did that reorder live in the meantime, and what triggered the retry?**

`SupplierGatewayImpl.orderReplenishment()` inserts the `supplier_orders` row — with its `BuyerRef`, its `X-Request-Id`, and status `PENDING` — *before* it ever makes an HTTP call to LegacySupply. So the moment the low-stock rule fired for `RO-2`, that reorder already existed durably in Postgres, independent of whether the network call that followed succeeded. When the immediate attempt (plus its in-request retries with backoff) still failed because LegacySupply was down, the row was simply left as `PENDING` rather than discarded.

From there, `PendingOrderRetryJob` — a `@Scheduled(fixedDelay = 10000)` background job — polls `SupplierOrderRepository.findPendingOrders()` every 10 seconds and calls `SupplierGatewayImpl.submitOrderWithRetry(...)` again for each one it finds, reusing the *same* persisted `BuyerRef` and `X-Request-Id` from the original row (not new ones). It kept retrying on that fixed interval through the roughly two-minute outage window until LegacySupply came back and accepted the request, at which point the row was updated in place to `PLACED` with `PoNumber = PO-100026`. So the reorder never lived anywhere but the database between the rejection and the eventual placement, and the trigger was that scheduled background job, not the original request thread or any manual action.

### Question 3

> **LegacySupply never tells you how long a session lasts. Measure your session lifetime from your own logs, state the number, and explain how your adapter decides when to sign in again.**

`LegacySupplyClient` treats a session token as good for `SESSION_TTL_SECONDS = 150` seconds before proactively requesting a new one, on the assumption that the real server-side expiry is around 180 seconds — i.e. it renews 30 seconds early on purpose rather than cutting it close. This account's own `/verify` record is consistent with that: the first order (`PO-100011`) was placed at 19:08:28 and the last recorded request was at 19:33:12, a session of about 1,484 seconds, during which LegacySupply counted 11 sign-ins — roughly one every ~148 seconds if spread evenly, which lines up closely with the 150-second proactive-refresh window rather than with, say, a much longer or much shorter cadence.

Because the adapter always renews before the real expiry is reached, our own traffic never naturally produces a session-expiry-triggered `401`/`E-AUTH-07` outside of the injected outage — the design intentionally avoids ever finding out the *exact* server-side number the hard way. The adapter's actual decision logic is two-layered: **proactively**, `getOrRenewSession()` checks a cached `Instant` and requests a new token if more than 150 seconds have passed since the last one; **reactively**, `executeWithSessionHandling()` catches any call that fails with HTTP 401 or error codes `E-AUTH-02`/`E-AUTH-03`/`E-AUTH-07`, forces an immediate re-sign-in, and retries that one call once with the fresh token — which is exactly the "5 requests with an expired session" that `/verify` recorded as successfully renewed.
